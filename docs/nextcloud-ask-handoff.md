# Personal Nextcloud question handoff

The Nextcloud Files sidebar sends a navigation URL to
`/platform/nextcloud-ask` only when its signed file-status check reports the
current source ETag as ready. The four URL selectors are `instance_id`,
`binding_id`, positive canonical `file_id`, and `source_etag`. They are
untrusted identifiers, not a bearer credential or a statement that the person
may use the knowledge base.

The page preserves that local route across password/LDAP or OIDC login. It
calls `GET /api/v1/integrations/nextcloud/ask-target` with exactly those four
selectors. This endpoint rejects API keys and requires the authenticated
interactive WeKnora user. It finds one active source pair, its matching
`published` source-version row, and the completed/enabled candidate for the
exact ETag. Then it checks the user's current KB and group read permissions
and calls the Nextcloud publication guard, which requires a fresh linked AD
identity and the current source permission/ETag. The target is reread after
the network check and the response is `no-store`.

On submit the page repeats that check, resets earlier chat selections, and
starts a personal quick-answer chat with the exact knowledge ID as the only
retrieval target. Search and answer paths keep their own KB and Nextcloud
source guards; the URL and target endpoint are never sufficient to read a
document. Later turns use ordinary WeKnora chat controls and still require
their own retrieval authorization. The Nextcloud machine connection is never
used as the questioner's identity.

The Nextcloud manifest now carries a separate `human_url` generated by its
Files route for the original file. The connector stores this as
`nextcloud_human_url` on the indexed candidate; the existing `url` remains the
machine content endpoint. Document citations and Markdown exports use the
human URL only when its file ID matches. Opening it relies on the visitor's
Nextcloud login and current share permission. Existing indexed candidates
need a source reindex to gain the citation link; the URL must be reachable
from the employee's browser on the LAN.

The endpoint intentionally does not include a signed launch token. This V1
jump requires the employee to authenticate separately to WeKnora and have a
valid linked AD principal. Embedded chat, delegated personal tokens, shared
login and stream/cancellation inside Nextcloud remain V1.1 work.

Tests cover exact published-target resolution, pair/version withdrawal,
interactive-principal enforcement, post-authorization recheck, URL validation,
frontend type checking and package compilation. A full two-user AD-to-citation
LAN run must still be performed against the built patch and app before
claiming the PRD's end-to-end question/citation acceptance.
